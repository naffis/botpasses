# Changelog

## Unreleased

- Security: a personal org gets a random id and records who created it (`orgs.created_by`, migration 010). An owner who was removed from the org they created no longer regains it by signing in; they land in a fresh org. An org a user created that has no members at all (a provisioning that stopped before the owner insert) is reclaimed instead of duplicated.
- Security: item envelopes written before AAD binding (bound to the org id alone) are re-encrypted under `org_id|item_id|allowed_hosts_json|inject` once at boot (`aad_rebind` log with `rebound`, `verified`, `unreadable`; `items.aad_version`, migration 010). The inject path no longer falls back to the legacy binding. `updateItem` writes a re-encrypted envelope and the columns it is bound to in one statement.
- Security: `rotateItem` enforces the 64 KiB value cap, and rotate, update, and delete by item id refuse production items on the staging deploy (404) like list and inject already did.
- Security: a grant for a trusted (`avt_`) client refuses method, path, and host limits at approve (400 `scope_unenforceable`), explicit or inherited from the request, because `/runtime/resolve` has no call to check them against; `max_calls` and `ttl_seconds` stay. Wrong approval-code attempts survive a code rotation (an agent re-requesting no longer resets the five tries) and `POST /api/grants/approve-by-code` is limited to 20 attempts per org per 15 minutes (429).
- Security: `GET /approve?token=` sends a session that has not passed the authenticator step to `/verify-totp` (or `/enroll-totp`) like a signed-out visitor goes to `/sign-in`, instead of a JSON 403.
- Changed: KEK rotation runs while serving. The hosted process accepts `VAULT_KEK_PREVIOUS_WRAPPED` (or raw `VAULT_KEK_PREVIOUS`, refused under `VAULT_KEK_REQUIRE_KMS=1`) next to the current KEK; an org DEK or the identity DEK still wrapped under the previous KEK opens and is re-wrapped in place (`dek_rewrapped` audit row and log line, `kek_previous_loaded` at boot). Boot refuses a previous key equal to the current one, both forms at once, or a bad length. `vault kek-rotate` stays for the offline pass and accepts `VAULT_KEK_NEW`. Runbook rewritten: set previous, deploy, rotate, remove previous.
- Changed: revoking a grant drops the `folder_standing` policy only when that grant was activated by it; revoking a prompt, session, or item grant leaves a folder-wide approval in place. Approving `item_standing` or `folder_standing` replaces a stale policy row for the pair instead of failing on the unique index. Grants are looked up per (client, item) pair through the `grants_client_item_status` index rather than by scanning the org, and the hourly sweep deletes revoked, consumed, and expired grants settled more than 30 days ago (`sweep_expired` logs `grants`; audit rows stay).
- Changed: the offsite backup envelope starts with `BPBK` and a version byte, authenticated with the body; `hosted-backup.ts decrypt` refuses a file without the magic or with an unknown version. Dumps written before this change do not carry the header and must be decrypted with the previous release.
- Repository: `clients_oauth_client_id` and `org_members_org` (migration 003) are in `schema.ts` too, and the Postgres parity test now checks indexes in both directions. Docs say what the item AAD is (README, threat model).
- Security: sign-in counters are atomic in the store. An email-code attempt is claimed with one conditional `UPDATE` before the hash check (`claimOtpAttempt`), so concurrent guesses cannot share a slot; `POST /api/auth/otp/verify` is limited to 25 attempts per email and 50 per address in 15 minutes, and a verify for an address with no live code costs the same scrypt work as a wrong code. Authenticator attempts are charged the same way (`claimTotpAttempt`), the replay guard and backup-code consumption are conditional updates (`consumeTotpStep`, `markBackupUsed` returns whether it consumed), so the same code or backup code passes exactly once even when submitted twice at once.
- Security: the CSRF token is signed for the session cookie it travels with; a token from another session is 403. On HTTPS only the `__Host-` cookies are read, only on a request the proxy marks `x-forwarded-proto: https`; a plain-named cookie is no longer a fallback (cookie tossing cannot fix a session). A cookie value that is not valid percent-encoding is ignored instead of a 500.
- Security: operator sessions are listed and revocable by the org they act in (`active_org_id` when still a member, else the first membership), not by every org the user belongs to. `listMembershipsForUser` orders by `joined_at NULLS FIRST, org_id` on both stores, so "first membership" is the same on SQLite and Postgres.
- Security: `VAULT_BOOTSTRAP_TOKEN` is refused at boot on staging and production unless `VAULT_BOOTSTRAP_ALLOW_PLANE=1` (break-glass window; unset both afterwards); a set token logs `bootstrap_token_enabled` at boot and every use logs `auth_bootstrap_used` with a token hash, address, method, and path. Proxy headers (`Fly-Client-IP`, `X-Forwarded-For`) are used for the caller's address only behind Fly or with `VAULT_TRUST_PROXY=1`; otherwise the socket peer counts.
- Security: `POST /api/orgs` requires a ready session (authenticator step passed), a printable name of 1 to 80 characters, and stays under the new per-user `orgs` plan limit (10; `VAULT_PLAN_LIMITS_JSON` key `orgs`, 402 `plan_limit`). Invites are limited to 10 per inviting account and 30 per address per hour (429).
- Fixed: `POST /api/auth/otp/send` emails first and stores the challenge only after delivery, so a mailer outage no longer leaves a dead code that blocks sign-in for ten minutes. A resend while a code is still valid sends a new code and expires the old one (it counts against the 5 per 15 minutes budget); the Resend button works.
- Fixed: session cookies carry the 7-day absolute lifetime instead of the 12-hour idle window, so the server-side idle extension is reachable: activity keeps a session alive for up to 7 days, an idle one still ends after 12 hours.
- Fixed: `auth_otp_sent`, `auth_otp_locked`, `auth_totp_verified`, `auth_session_revoked`, `auth_signed_out`, and `auth_bootstrap_used` log lines are emitted. The console follows a 403 `mfa_required` to `verify_url` or `enroll_url` instead of showing an error.
- Fixed: OAuth consent completes in a real browser. The consent page's script posted the decision and then read the redirect's `Location`, which browsers hide from scripts, so Allow never left the page. `POST /consent` now answers a caller that sends `Accept: application/json` with `200 { location }` and the page navigates there itself; Node clients and a no-script form submit keep the 303. A Chromium smoke test registers a client, opens `/oauth/authorize`, clicks Allow, lands on the redirect URI with a code, and exchanges it.
- Fixed: re-enrolling an authenticator from the console shows a QR code. `/enroll-totp` sent a ready operator straight back to the console, and the page would have started a second secret anyway. The page now renders while a re-enroll secret is in flight and reads it back through the new `GET /api/auth/totp/pending` (the same `otpauth_url` and `qr_svg` that `totp/start` returned, live for ten minutes), calling `start` only when nothing is pending. A reload during first enrollment keeps its secret the same way. The console's code dialog also accepts a 10-character backup code now (it cut input at 8 characters, so a backup code could never pass), and says so. A Chromium smoke test re-enrolls from the console with a backup code and confirms the new secret.
- Changed: console, auth, and collect assets are referenced at content-hashed paths (`/assets/console.<sha8>.js`) and served `immutable`; the plain names still resolve but are `no-cache`, so a deploy can no longer be pinned to a stale bundle by a year-long cache.
- Security: JSON routes require `Content-Type: application/json` (415 otherwise; a bodiless POST still reads as `{}`), so a cross-site HTML form can never reach a JSON handler whatever the CSRF check says. `POST /approve` and `POST /consent`, which back HTML forms, also accept a form body.
- Security: the marketing site is served only on an allowed `Host`, like every other page; a foreign or loopback `Host` on a public plane is refused. Health, readiness, discovery, and assets still answer on any Host.
- Repository: the unused `src/hosted/collect-js.ts` is gone (the collect page has been served from the client bundle); `/consent` and `/device` are only mounted with the OAuth provider instead of falling back to an unbacked form.
- Security: hosted boot refuses `VAULT_AUTH_MODE=test` outright (the process never installs header principals) and requires `VAULT_DEPLOY_PLANE` to be `staging` or `production`; an unset plane used to mean production and skipped the plane guards. `VAULT_APPROVAL_HMAC` must be 64 hex characters, the kernel refuses a key under 32 bytes, and approval links are bound to the org they were minted for. `createHostedServer` without an `authResolver` now authenticates nobody instead of trusting test headers.
- Security: `vault serve` prints two loopback bearers instead of one. The operator bearer opens `/api` and the console; the model bearer opens `POST /mcp`; each is refused on the other surface, so an MCP client can no longer approve its own grants. `vault mcp --remote` forwards stdio to a running `vault serve` with the model bearer. The local server answers only to a loopback `Host`, caps JSON bodies at 128 KiB, sends a nonce CSP on the console, and no longer echoes driver or parser errors. `vault set --value` is gone: pipe the value or type it at the no-echo prompt. `master.key` is refused when group or others can read it.
- Security: behind Cloudflare the rate-limit address comes from `CF-Connecting-IP` only when the address Fly saw is inside `VAULT_TRUSTED_PROXY_CIDRS` (default: Cloudflare's published ranges; empty disables the header). Deploy and backup secrets move to GitHub environments (`staging`, `production`, `backup`) and `flyctl deploy` names its app with `-a`; `deploy-prod` also refuses a SHA with no successful `deploy-staging` run.
- Fixed: one request id per request. The inbound `x-request-id` (or the minted one) is now the same value in the access log, the `request_error` line, the 500 body, and the Sentry event; error messages are redacted before they are logged. A malformed percent-escape in `/collect/:id` or a site path is a 400 or 404 instead of a 500 plus a Sentry event; `/ready` caches its database ping for 5 s. Errors after headers are sent are logged under the request id and the stream is cut; a site file stream error no longer ends the response as if complete.
- Changed: the hosted server sets `headersTimeout` 15 s, `requestTimeout` 30 s, and `keepAliveTimeout` 65 s (SSE streams exempt); one principal may hold at most four open `GET /mcp` streams (429 past that). Signal handlers are installed before the boot-time sweep; `vault serve` in hosted mode installs the process guards; a plane without `SENTRY_DSN` logs `sentry_dsn_missing`. Docs: `.env.example` lists `VAULT_TRUST_PROXY`, `VAULT_TRUSTED_PROXY_CIDRS`, `VAULT_BOOTSTRAP_ALLOW_PLANE`, `VAULT_OIDC_PREVIOUS_JWK`; `docs/ops/migrations.md` covers statement timeouts.
- Security: a revoked OAuth agent stays revoked. Only a fresh consent (authorization code or device code) reactivates the `(org_id, oauth_client_id)` row; a refresh token held by another member of the same org for the same client id is refused with `invalid_grant`, and revoking the agent destroys every consent the org's members gave for that client id, not only the first consenter's. Consent binds the org the operator session acts in into the OAuth grant, the access JWT carries it as `org_id`, and `/mcp` checks the account is still a member of that org instead of picking the account's first membership (verification no longer provisions an org). Authorization codes, device codes, and refresh tokens are consumed with one conditional write, so two concurrent exchanges of the same code cannot both succeed.
- Security: `POST /oauth/revoke` denylists JWT access tokens (verified against this server's keys and bound to the calling client), and revoking a refresh token, or replaying a rotated one, marks every access token issued under the same grant in the ledger (`access_events.grant_id`, migration 012). Client ID Metadata Document fetches are limited per requesting IP (10 per hour) as well as per target host (30 per hour), capped at 4 in flight, and time out after 3 s. `POST /device` user-code attempts are limited to 10 per 15 minutes per IP and per OP session. JWT verification allows 30 s of clock skew, no more. DPoP is off (nothing enforced it).
- Changed: the OAuth server accepts only what discovery advertises: `token_endpoint_auth_methods_supported` is `["none"]` (dynamic and CIMD clients are public clients), `response_types_supported` is `["code"]`, and `response_modes_supported` lists the modes the engine really serves (`query`, `fragment`, `form_post`); the engine and the document are built from one set of constants. `POST /api/clients/:id/rotate` on a revoked agent is 409. `VAULT_OIDC_PREVIOUS_JWK` publishes the key being rotated out in JWKS and keeps verifying tokens it signed; new tokens are always signed with `VAULT_OIDC_PRIVATE_JWK`. Runbook: `docs/ops/oidc-key-rotation.md`.
- Removed: the AgentPass Authority stub (`/agentpass/*`, `VAULT_AGENTPASS`, the `agentpass` list on `GET /api/inbox`). It reported pending passes as allowed, never used its signing key, and validated without authentication; the table `agentpass_passes` stays (schema is expand-only) and is unused.
- Fixed: the OAuth request handler now settles once oidc-provider has answered (it awaited a Koa `next` that never fires), so every OAuth request no longer leaves a pending promise behind.
- Fixed: the production image builds again. The site stage now carries the three repository files the site build reads (`src/brand-visual.ts`, `CHANGELOG.md`, `docs/security/threat-model.md`); `.dockerignore` lets those two Markdown files through. CI gained an `image` job that runs `docker build` and checks the image exits 78 on an unsafe configuration.
