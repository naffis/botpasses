# Changelog

## Unreleased

- Fixed: MCP OAuth dynamic client registration accepts RFC 8252 loopback `http://localhost:<port>/…` as well as `127.0.0.1` and `[::1]`. Cursor (and other hosts) register `http://localhost:8787/callback` in the same DCR set as `cursor://…` and `https://www.cursor.com/agents/mcp/oauth/callback`; rejecting localhost used to fail the whole registration with `redirect_uri must be https, loopback http…`. The `avm_` Bearer path is unchanged. `javascript:`, `data:`, `file:`, and `http` to a non-loopback host are still refused.
- Fixed: an unauthenticated `GET /mcp` (SSE listen) is still 401, but no longer sends `WWW-Authenticate` with protected-resource metadata, so a stream probe does not start OAuth dynamic client registration. Unauthenticated `POST /mcp` `tools/call` still 401s with that challenge. DCR now accepts the `grokbot:` desktop scheme and logs `dcr_redirect_rejected` with scheme and reason only.
- Changed: user connect uses one redirect URI for every provider: `https://botpasses.com/connect/callback` on production, `https://staging.botpasses.com/connect/callback` on staging, and `http://127.0.0.1:8888/callback` locally. The Store credential and Collect forms show and copy that URI next to Kind when Kind is Client ID and secret; the Connect dialog shows it again before opening the vendor. `/integrations/:provider/callback` stays as an alias for apps that already registered it.
- Security: operator inboxes (users, invites, OTP lookup) and live OAuth adapter bearers (refresh, auth code, device code, access token, session, interaction) are stored as a keyed HMAC plus an AES-GCM wrap under the identity DEK. Grant ids stay plaintext so revoke still joins. Magic-link tokens are stored as SHA-256, not the URL token. A Neon dump without the platform KEK no longer yields inboxes or those tokens. Item names, last-4, hosts, and Grant ids remain. Rollback runs `scripts/email-restore-plaintext.ts` and `scripts/oidc-restore-plaintext.ts` before reverting the image.
- Site: `/security` names bound item AAD (`orgId|itemId|allowed_hosts_json|inject`), email-at-rest, and OAuth-token-at-rest. Last-4 is not stripped from connector bodies. The raw origin cap is 1 MiB, then redact, then 256 KiB. A dump without the KEK hides values, inboxes, and bearer tokens, not names. Bootstrap MFA is skipped only with `VAULT_BOOTSTRAP_ALLOW_PLANE=1`.
- Infra: CI smoke installs Playwright Chromium from Playwright's CDN, not Google's Chrome apt repo, so a Packages.gz hash mismatch cannot fail the job.

Navy ticket at `/mark.svg`; white ticket at `/mark-on-dark.svg` (dark surfaces and social cards). Favicon is the simplified eyes, perforation, and barcode on a navy tile. The result is `{ status: "user_connect_required", provider, item_name, refresh_item_name, connect_url, need_id, hint }` with `next` steering; nothing is sent, so a one-call approval comes back instead of being spent on a 401. Its Connect button, and the `connect_url` deep link (`#credentials/item/<id>?connect=&agent=&need=`), open the connect dialog with the Client ID prefilled and "Also allow <agent> to use the connected account" checked, so the callback writes the agent's standing policy on the refresh item, closes the card (`need_fulfilled`), and the agent's retry succeeds through the user-token path without a second approval. The local plane returns the same status without `connect_url` and a hint naming `vault set <ITEM>_REFRESH --inject refresh`.
- Infra: the GitHub default branch is `dev`, so `deploy-staging` can run after `ci` on `dev`. Provider-test fixtures no longer use Slack-shaped token strings that gitleaks treated as leaks.
- Fixed: the hosted Postgres pool no longer sends `statement_timeout` or `options` as startup parameters. Neon `-pooler` (PgBouncer) refuses those, so the process never listened and Fly's `/ready` check failed. Client-side connect/idle timeouts and `application_name` stay. Fly HTTP check grace is 60 s.
- Infra: `deploy-staging` starts a Machine flyctl left stopped and waits until `https://botpasses-staging.fly.dev/ready` is 200, so a rolling-update leftover cannot go green while the origin is down.
- Fixed: a leftover `VAULT_BOOTSTRAP_TOKEN` on staging without `VAULT_BOOTSTRAP_ALLOW_PLANE=1` no longer exits 78. Auth still ignores the token; boot logs `bootstrap_token_ignored`. The previous refuse-to-boot guard crash-looped the Fly Machine.
- Security: the browser-side CSRF cookie readers (console and collect bundles, the auth pages, the invite page) read `__Host-bp_csrf` first and fall back to the plain `bp_csrf` only when the host-prefixed cookie is absent. A plain cookie a subdomain plants can no longer shadow the real token and break every mutation on the HTTPS origin.
- Security: the hosted entry point (`npm run hosted`, `startHosted`) refuses to start without `VAULT_MODE=hosted` (exit 78 with a message naming it). Every hosted boot guard is keyed on that mode, so an unset mode used to run the process with no plane check, an empty session secret, test auth accepted, and a bootstrap token needing no flag. `VAULT_OIDC_PREVIOUS_JWK` with the wrong shape is now the same exit 78 at boot instead of exit 1 after the KEK was unwrapped and Postgres opened.
- Security: proxy headers are trusted per header. `Fly-Client-IP` counts only on Fly (`FLY_APP_NAME`); behind a proxy the deployer runs (`VAULT_TRUST_PROXY=1`) only the last `X-Forwarded-For` hop counts, so a client can no longer choose its own address for every rate limiter, or claim a Cloudflare address to unlock `CF-Connecting-IP`, by sending a Fly header. The request id follows the same rule: `Fly-Request-Id` is reused on Fly, a client-chosen `x-request-id` is never reused, and a UUID is minted everywhere else.
- Security: `POST /mcp` on `vault serve` is one session per client. `initialize` answers with an `Mcp-Session-Id` header (400 without it on later frames, 404 when unknown or idle for 8 hours), so a second client's `initialize` no longer renames the agent that another client's grants are keyed on. `vault mcp --remote` carries the header. Stdio `vault mcp` is unchanged: one session per process.
- Fixed: local `POST /api/items` and `/api/secrets` take `username` (HTTP Basic user, OAuth client id, or AWS access key id; `null` clears it), and the local console's store form has a username field, which HTTP Basic requires.
- Docs: the self-hosting page shows hosted mode started with `VAULT_BIND_HOST` and `PORT` (the `--host` and `--port` flags are local only), lists `VAULT_BIND_HOST`, `PORT`, and `VAULT_SITE_ROOT`, and no longer lists `VAULT_TRUST_PROXY` twice; `.env.example` lists `VAULT_KEK_NEW`.
- Fixed: an allowlisted API answering 204, 205, or 304 (a `DELETE` that returns no content) or a status outside 200 to 599 through the pinned TLS path threw inside the HTTP parser callback, which ended the hosted process and never settled the call. The connector no longer builds a WHATWG `Response` there: a bodiless answer comes back with its status and headers and an empty `body`; a status no client may carry is a 502 `bad_status`. Both count as an origin answer, so a one-call approval stays spent.
- Security: the `body_too_large` result (an origin body over 1 MiB) returned its origin headers unredacted; a `Link` header echoing a `query:<param>` key reached the model. Its headers are now redacted like every other answer's. `http_request` refuses double-encoded separators and dots (`%252F`, `%252E`, and deeper), a percent-encoded NUL (`%00`, `%2500`), and control characters in `path`, which an origin could decode again.
- Fixed: a refresh-token exchange for a stored `<ITEM>_REFRESH` sent only `refresh_token` and `client_id`, which every provider except a PKCE public client refuses with `invalid_client`. The exchange now authenticates the app the way the connect exchange did: the client secret item goes out as HTTP Basic (Spotify, Slack) or as `client_id` and `client_secret` form fields (GitHub, Google, Stripe Connect), the refresh token rides in the form, both items must allow the token host, and neither value reaches the result or the audit. The same holds when an agent posts `<ITEM>_REFRESH` to the token endpoint itself through `http_request`: it needs only its approval on the refresh item, Botpasses reads the sibling client secret (`<ITEM>_SECRET`, then `<ITEM>`, same environment), builds the exchange per the provider's token auth, returns the redacted body with `refreshed: true` and `token_last4`, caches the user token, persists a rotated refresh token (`refresh_rotated`), and audits `inject` for both items. Without a sibling, a PKCE provider gets the public-client exchange; any other provider is refused before dialing with `inject_denied` and `missing_item` instead of a vendor `invalid_client`.
- Fixed: a token endpoint that answered 2xx with an unusable body (not JSON, no `access_token`) was audited `inject_failed` although the credential had been sent; the row is `inject`. `inject_failed` now means only that the origin was unreachable before the TLS handshake.
- Fixed: `http_request` with `dry_run` reported an expired or spent standing policy as `standing`; it now applies the same liveness test a real call does and reads the stale row past without deleting it.
- Fixed: the console's plain Approve on a trusted (`avt_`) client's grant was refused with `scope_unenforceable` whenever the agent had stated a call, because the request's method, host, and path were inherited. A plain approve for a trusted client is written unrestricted; an explicit `methods`, `path_prefixes`, or `hosts` is still refused.
- Changed: the `next.for_model` steering for a `body_too_large` answer tells the model the response was over 1 MiB and to narrow the call (pagination, a smaller page, a fields filter) instead of "retry once", which spent another one-call approval on the same oversized answer.

- Security: a personal org gets a random id and records who created it (`orgs.created_by`, migration 010). An owner who was removed from the org they created no longer regains it by signing in; they land in a fresh org. An org a user created that has no members at all (a provisioning that stopped before the owner insert) is reclaimed instead of duplicated.
- Security: item envelopes written before AAD binding (bound to the org id alone) are re-encrypted under `org_id|item_id|allowed_hosts_json|inject` once at boot (`aad_rebind` log with `rebound`, `verified`, `unreadable`, `batches`, `stopped`, `ms`; `items.aad_version`, migration 010). The inject path no longer falls back to the legacy binding. `updateItem` writes a re-encrypted envelope and the columns it is bound to in one statement. The rebind runs after the server listens, so `/health` and `/ready` answer inside the Fly check's grace period on a large table, and reads rows in pages of 200 (`aad_rebind_progress` per page; memory bounded by one page). The signal handlers are installed before it: a `SIGTERM` during the pass ends it at the next page boundary and the drain waits for the page in flight before closing the pool. Runbook rewritten: set previous, deploy, rotate, remove previous.

Approving `item_standing` or `folder_standing` replaces a stale policy row for the pair instead of failing on the unique index. Grants are looked up per (client, item) pair through the `grants_client_item_status` index rather than by scanning the org, and the hourly sweep deletes revoked, consumed, and expired grants settled more than 30 days ago (`sweep_expired` logs `grants`; audit rows stay).
- Changed: the offsite backup envelope starts with `BPBK` and a version byte, authenticated with the body; `hosted-backup.ts decrypt` refuses a file without the magic or with an unknown version. Dumps written before this change do not carry the header and must be decrypted with the previous release.
- Repository: `clients_oauth_client_id` and `org_members_org` (migration 003) are in `schema.ts` too, and the Postgres parity test now checks indexes in both directions. Docs say what the item AAD is (README, threat model).
- Security: sign-in counters are atomic in the store. An email-code attempt is claimed with one conditional `UPDATE` before the hash check (`claimOtpAttempt`), so concurrent guesses cannot share a slot; `POST /api/auth/otp/verify` is limited to 50 verifies per address and 25 wrong codes per email in 15 minutes (a verify for an address with no live code, or a correct code, does not spend the per-email budget, so bogus verifies posted for someone else's address cannot lock that person out), and a verify for an address with no live code costs the same scrypt work as a wrong code. Authenticator attempts are charged the same way (`claimTotpAttempt`), the replay guard and backup-code consumption are conditional updates (`consumeTotpStep`, `markBackupUsed` returns whether it consumed), so the same code or backup code passes exactly once even when submitted twice at once. Confirming an enrollment consumes the pending secret with one conditional update (`consumePendingTotp`), so two concurrent confirms of the same code replace the secret and mint backup codes exactly once.
- Security: the CSRF token is signed for the session cookie it travels with; a token from another session is 403. On HTTPS only the `__Host-` cookies are read, only on a request the proxy marks `x-forwarded-proto: https`; a plain-named cookie is no longer a fallback (cookie tossing cannot fix a session). A cookie value that is not valid percent-encoding is ignored instead of a 500.
- Security: operator sessions are listed and revocable by the org they act in (`active_org_id` when still a member, else the first membership), not by every org the user belongs to. `listMembershipsForUser` orders by `joined_at NULLS FIRST, org_id` on both stores, so "first membership" is the same on SQLite and Postgres.
- Security: `VAULT_BOOTSTRAP_TOKEN` is honoured on staging and production only with `VAULT_BOOTSTRAP_ALLOW_PLANE=1` (break-glass window; unset both afterwards). A leftover token without the flag is ignored (`bootstrap_token_ignored`) and does not fail boot. When the token is live it logs `bootstrap_token_enabled` at boot and every use logs `auth_bootstrap_used` with a token hash, address, method, and path. Proxy headers (`Fly-Client-IP`, `X-Forwarded-For`) are used for the caller's address only behind Fly or with `VAULT_TRUST_PROXY=1`; otherwise the socket peer counts.
- Security: `POST /api/orgs` requires a ready session (authenticator step passed), a printable name of 1 to 80 characters, and stays under the new per-user `orgs` plan limit (10; `VAULT_PLAN_LIMITS_JSON` key `orgs`, 402 `plan_limit`). Invites are limited to 10 per inviting account and 30 per address per hour (429).
- Fixed: `POST /api/auth/otp/send` emails first and stores the challenge only after delivery, so a mailer outage no longer leaves a dead code that blocks sign-in for ten minutes. A resend while a code is still valid sends a new code and expires the old one (it counts against the 5 per 15 minutes budget); the Resend button works.
- Fixed: session cookies carry the 7-day absolute lifetime instead of the 12-hour idle window, so the server-side idle extension is reachable: activity keeps a session alive for up to 7 days, an idle one still ends after 12 hours.
- Fixed: `auth_otp_sent`, `auth_otp_locked`, `auth_totp_verified`, `auth_session_revoked`, `auth_signed_out`, and `auth_bootstrap_used` log lines are emitted. `auth_session_revoked` is written after the session is deleted, so a refused attempt (an operator on another member's session, 403) is not logged as a revocation. The console follows a 403 `mfa_required` to `verify_url` or `enroll_url` instead of showing an error.
- Fixed: OAuth consent completes in a real browser. The consent page's script posted the decision and then read the redirect's `Location`, which browsers hide from scripts, so Allow never left the page. `POST /consent` now answers a caller that sends `Accept: application/json` with `200 { location }` and the page navigates there itself; a caller that sends the CSRF header without that `Accept` keeps the 303. A form submit without the header (scripts off) is 403: the consent form carries no CSRF field and `POST /consent` needs the double-submit token like every other cookie-session mutation. A Chromium smoke test registers a client, opens `/oauth/authorize`, clicks Allow, lands on the redirect URI with a code, and exchanges it.
